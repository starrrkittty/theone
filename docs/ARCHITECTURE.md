# Agent A 架构与技术边界

## 目标

Agent A 的职责是把连续、嘈杂的视频感知结果转换成可验证的动作事实。它不能只做一次“最大概率判断”，也不应该让 LLM 代替稳定的数值计算。

## 在线数据流

1. App 建立用户与 AI 私教的视频通话。
2. App 端用 MediaPipe 从画面提取 33 点人体骨架；默认不上传原视频。
3. 可选分类器（浏览器 ST-GCN 或独立 ActionCLIP）给出动作概率分布。
4. A 端校验、Kalman 平滑、特征提取，并融合 HMM、人体几何规则和外部概率。
5. 候选动作必须满足置信度、概率间隔、持续帧数和安全切换窗口，才能确认为当前运动。
6. 对应专项模块计算阶段、次数/保持时长、关节角和姿态问题。
7. 报告构建器聚合连续错误、质量下降和指导优先级，输出 `ActionReport v2`；每份报告带 `report_id/session_generation/sequence`，角度附带本帧关键点可见度证据。
8. A 只在动作确认/切换、持续错误、疲劳趋势或安全事件达到门槛时发出 `coach_trigger`；B 端据此路由专项教练，用 LLM 处理对话、语境、计划、饮食与主动关怀。

## 为什么不让 LLM 直接读 URDF

URDF 是结构化 XML，适合解析器而不是生成模型。LLM 直接阅读整份文件会带来三个问题：

- 每帧重复携带大量稳定信息，浪费上下文和费用。
- 关节名称、上下限和父子关系需要确定性，不应接受生成式幻觉。
- LLM 不擅长高频、低延迟的角度运算和阈值判断。

因此本仓库用 `backend/kinematics/urdf_loader.py` 一次性解析 URDF，校验关节映射，并向下游暴露紧凑关节表。实时帧只传变化的角度、阶段和错误。LLM 收到的是动作语义，而不是机器人文件。

## 识别状态机

```text
unknown
  -> candidate（有动作证据，但尚未稳定）
  -> confirmed（连续多帧满足阈值）
  -> switched（另一动作持续占优且位于安全切换窗口）
```

只有 `confirmed` 或 `switched` 才产生一次 `recognition_event`。App 可直接播放事件中的文案，随后保持安静。`agent_context.should_coach_now` 是连续错误状态，`coach_trigger.triggered` 才是去抖和冷却后的跨端调用信号；B 网关会拒绝无新触发的自动请求。用户主动提问通过顶层 `user_initiated=true` 明确旁路主动播报冷却。

## 外部模型适配协议

客户端可在 WebSocket 帧中附加：

```json
{
  "client_probs": {
    "squat": 0.82,
    "pushup": 0.05,
    "plank": 0.07,
    "unknown": 0.06
  }
}
```

当前允许标签为 `squat`、`pushup`、`plank`、`bicep_curl`、`alternate_bicep_curl`、`unknown`。服务端会裁剪到 0–1、丢弃非有限值/未知标签，并要求第一、第二候选之间存在足够间隔。外部模型是证据之一，不直接绕过时间确认和安全切换。

## A 与 B 的协议稳定性

- `schema_version` 必须随破坏性字段变化升级。
- B 只依赖 `ActionReport` 和事件，不依赖 A 内部 HMM、MediaPipe 序号或 URDF 格式。
- `report_id` 是请求、回复和日志关联键；B 回复必须原样回传，App 可据此丢弃迟到的旧回复。
- `joint_angles` 缺失表示本帧没有可靠测量，不能按 0 度解释；`joint_confidences` 是贡献关键点 visibility 的最小值，不是角度误差标定结果。
- A 可以更换姿态模型或增加分类器，只要保持协议兼容。
- B 不得用 LLM 重新计算角度或覆盖高优先级安全信号。

## 下一阶段的合理顺序

1. 收集每类动作的短视频回放集，建立识别准确率、首次确认延迟和误切换率基线。
2. 增加多人主体锁定；多人时先可靠选择主用户，再谈复杂动作识别。
3. 把 ActionCLIP 作为独立可选服务做 A/B 对比，不先把重依赖写死进主进程。
4. 使用通话回放测试弱网、低光、遮挡、横竖屏和语音打断。
5. 只有开源特征和规则达到瓶颈、且有标注集与明确指标时，再讨论微调或训练。
